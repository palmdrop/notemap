# Review: Authentication (login, sessions, tokens, the door)

**Date**: 2026-09-01
**Status**: Resolved
**Scope**: `apps/daemon/src/auth/`, `apps/daemon/src/middleware/authenticate.ts`, `apps/daemon/src/routes/session.ts`, `apps/daemon/src/routes/tokens.ts`, `apps/daemon/src/routes/health.ts`, `apps/daemon/src/app.ts`, `apps/daemon/src/cli/`
**Plan**: `docs/plans/login-and-access-tokens.md`
**Spec**: `docs/specs/security.md`, ADR 27

---

## Overall

The mechanism is sound and matches the spec closely: parameterised SQL, `timingSafeEqual`
everywhere, secrets stored as SHA-256 digests, scrypt for the password, session-id regeneration on
login, the `session-required` containment `403`, `HttpOnly`/`SameSite=Lax`/`Secure` cookies, no CORS
headers, `0600` on the auth database, and health that withholds the pool identity until authenticated.
Live testing against a throwaway daemon (password set, `127.0.0.1:47471`) confirmed all of these hold.

One real defect surfaced under load, and it is the one the spec explicitly claims is closed: **the
login throttle is a check-then-act with the increment deferred behind the scrypt hash, so it does
not gate concurrent bursts.** That both defeats the anti–brute-force intent and turns the one
unauthenticated route into a memory/CPU amplifier. Everything else below is design-note or minor.

Nothing in scope is marked **Done** in the plan (it is **In progress**), so there is no `Shipped:`
trail gap to flag yet — but see finding 4.

## Bugs

### 1. The login throttle does not gate concurrent attempts, and scrypt runs before the counter moves

`apps/daemon/src/routes/session.ts:17-36`, `apps/daemon/src/auth/throttle.ts:19-34`

The handler reads the gate, then does the expensive work, then records the failure:

```
throttle.waitFor()  (line 17)  → 0 for every request in a simultaneous batch
await auth.login(...) (line 29) → full memory-hard scrypt hash, per request
throttle.failed()   (line 32)  → only now is the counter advanced
```

`openAt`/`failures` are only ever advanced inside `failed()`, which runs *after* the `await`. Any
number of requests that arrive before the first one finishes hashing all see `waitFor() === 0` and
all proceed to scrypt. It is a TOCTOU on the throttle.

Measured against the live daemon (`FREE = 5`):

```
30 requests, sequential  → 1× reached the hash, 29× 429   (throttle works)
30 requests, concurrent  → 30× reached the hash, 0× 429   (throttle bypassed)
200 requests, concurrent → 200 hashes, 11.4s wall, peak RSS +256 MiB from ~83→348 MiB
```

Two consequences, both of which the spec claims are handled:

- **Brute-force.** `security.md` ("The login is throttled…") promises "the attacker's rate is
  capped either way." It is not. The free-attempt count is effectively "however many you can hold
  in flight," and an attacker repeats a burst each time the (30 s-capped) window reopens — turning
  the intended ~1 guess / 30 s into ~N guesses / 30 s.
- **Denial of service.** The same section argues the design "answers rather than waits" so an
  attempt costs nothing to hold. But the costly thing is the scrypt hash, and it runs *before* the
  gate can engage. On "the small machines this is meant to run on," an unauthenticated caller
  forces an unbounded batch of 128 MiB-class hashes (bounded only by the libuv threadpool draining
  them), repeatable every window. The throttle re-engages after each burst (I confirmed the `429`
  returns), so this is a bypass of the free-count, not a total failure — but the expensive path is
  never protected.

Fix: advance the counter *before* awaiting the hash, not after — e.g. reserve an attempt
synchronously at entry and settle it on the result, or cap the number of in-flight login
evaluations. The gate has to close before the work starts, not after it finishes.

## Design

### 2. The expensive hash is reachable without any credential and has no concurrency ceiling

`apps/daemon/src/routes/session.ts:29`, `apps/daemon/src/auth/passwords/scrypt.ts:20-28`

Independent of finding 1's ordering bug: `POST /v1/session` is one of three open routes, and it is
the only open route that does real work. scrypt at `N=2^16, r=8, p=2` is ~128 MiB and hundreds of
ms per call by design. Nothing bounds how many run at once. Even with a correct throttle, the first
burst before the counter clamps is a resource spike (measured +256 MiB from a single 200-wide
burst). Worth a hard ceiling on concurrent login evaluations regardless of how finding 1 is fixed —
the throttle is a rate limit, not a concurrency limit, and this route needs both.

### 3. Throttle failures forgotten after 15 min, but the escalation caps at 30 s

`apps/daemon/src/auth/throttle.ts:6,29` — `FORGET_MS = 15 min`, `CAP_MS = 30 s`. Once past the
threshold every new failure sets `openAt = now + 30 s` at most, so a patient attacker's steady-state
cost is 30 s per burst whatever the history. This is consistent with the spec's "escalates to a cap
and never becomes a lock," and is the right call against lockout-as-DoS — noting it so the 30 s
ceiling is understood as the real per-burst floor an attacker pays, which finding 1 currently lets
them pay for a whole batch rather than one guess.

## Minor

### 4. Plan/spec drift: CSRF and `Origin` checking still open, and the throttle claim is now false

`docs/specs/security.md` ("The login is throttled, and nothing else is") states the attacker's rate
is capped and an attempt costs nothing to hold. Finding 1 makes both untrue under concurrency. When
1 is fixed, the wording is fine; until then the spec overstates the control. Also still open per the
plan's own "What is still open": `hono/csrf` / `Origin` check beside `SameSite` (phase 3), and
phase 7's item-by-item answers. These are tracked, not surprises — flagged only so the throttle
claim gets corrected in the same change as the fix.

### 5. WAL/SHM sidecars rely on SQLite's inherited mode, not an explicit chmod

`apps/daemon/src/auth/store/index.ts:24-26` chmods `auth.db` to `0600` but not `auth.db-wal` /
`auth.db-shm`, which SQLite creates and which hold the same secret digests. On this run they came
out `0600`, but that is SQLite/umask behaviour rather than something the code asserts. A stricter
umask elsewhere or a future WAL-mode change could widen them. Low severity (digests, not
plaintext), but the guarantee is only as strong as the file the code actually sets.

## Non-issues

- **`//v1/feed`, `/V1/feed` reaching the SPA shell (200)** — these are not `/v1/...` paths. The
  double slash and the uppercase mean the request never matches the `/v1/*` guard *or* any API
  route, so it correctly falls through to the static app shell (HTML, no pool data). No pool route
  answers under either shape; confirmed `/v1//feed`, `/v1/./feed`, `%2f`, trailing-dot, and encoded
  variants all `401`.
- **`/v1/../secret` → 200 shell** — curl normalises this to `/secret` client-side; the server sees a
  non-`/v1` path and serves the shell. Not a traversal.
- **Static path traversal (`/../../etc/passwd`, encoded, double-encoded) → 200 shell** — `fileFor`
  in `ui/serve.ts` resolves and re-checks containment, and unmatched extensionless paths serve the
  shell rather than a file. No file outside `UI_DIR` was served; `/etc/passwd` was never returned.
- **Session id used as a `Bearer` token → 401** — the token prefix (`nmp.`) is required for the
  bearer path, so a cookie value cannot be replayed as a token. Confirmed.
- **Access token on `/v1/tokens`, `POST /v1/tokens`, `DELETE /v1/sessions` → 403 `session-required`**
  — the containment rule works exactly as specified; a token cannot mint its replacement or end
  sessions.
- **No `Access-Control-Allow-*` on any response, including with `Origin: evil.example`** — verified;
  the no-CORS property holds. (Preflight `OPTIONS /v1/feed` returns `401` because auth runs first;
  harmless, as no cross-origin use is intended.)
- **SQL injection in `name`** — parameterised; a `"; DROP TABLE credential;--` name authenticated
  as a normal failure and left the credential intact.
- **Username enumeration** — `login` runs `verifyPassword` against the stored hash and then a
  constant-time name compare whatever the name was, so a wrong name and a wrong password cost the
  same. No timing tell observed.
- **Health withholds pool identity when unauthenticated** — `{version}` only until a session or
  token is presented, then `{pool, version}`. Matches the acceptance criterion.
- **auth.db is `0600`** — confirmed on disk.

## Resolution

**2026-09-01.**

**1 — fixed.** The throttle's interface changed from `waitFor`/`failed`/`passed` to a single
`begin()` returning either a wait or the one attempt it reserved, with a `settle(worked)` to close
it. The count moves synchronously at entry and the result settles it, so the ordering the bug
depended on is no longer expressible from the route. `apps/daemon/src/auth/throttle.ts`,
`apps/daemon/src/routes/session.ts:15-37`. A route test drives 20 sign-ins concurrently and holds
that exactly one reaches the hash.

**2 — fixed, by the same seam.** A reserved attempt is held until it settles, and `begin()` turns
away anything arriving beside it. One login evaluation runs at a time, which is the concurrency
ceiling the finding asked for; a burst is now one scrypt rather than the free count of them. That
is defensible because the daemon is single-user: two sign-ins at once is never somebody mistyping.

**3 — noted, unchanged.** The 30 s cap stands as specified; the per-burst floor it describes is now
one guess per burst rather than a batch, which is what made the note worth writing.

**4 — fixed.** `security.md`'s throttle section states the counting order and the one-at-a-time
rule; a `Shipped:` entry records it. `hono/csrf` is now **declined with reasoning** rather than
left open — see the new section, and the finding below that came out of writing it.

**5 — not a defect.** SQLite's unix VFS creates `-wal` and `-shm` with the mode of the database
file, which is why the `chmod` is deliberately placed before the first write; the comment at
`store/index.ts:23-26` says so. Confirmed under `umask 000`: all three files land `0600`. The
existing test asserted the mode of every file in the directory but only named `auth.db`, so it
would have passed vacuously had the sidecars not been there; it now names all three.

### Found while answering the `hono/csrf` question

`requireJsonBody` returns early for a route that declares **no body**, or one whose body is optional
and absent, without looking at `Content-Type`. So `POST` on `.../archive`, `.../unarchive`,
`.../mark-processed`, `.../retire`, `.../unretire` and `.../cancel` accepts a simple cross-site
`POST` — which makes `security.md`'s "No `/v1` write is reachable that way today" false. What holds
them is `SameSite=Lax`, which is same-*site* and not same-*origin*, so a sibling subdomain of the
deployment carries the cookie; past that it is an unguessable id, which is obscurity. **Fixed.** `requireJsonBody` now asks every
`POST`, `PUT` and `PATCH` under `/v1` for `application/json`, carrying a body or not; the asset
upload stays the one exception, and `PUT` is never a simple method. The three early-outs and the
body-framing check they needed are gone with it. That forces the preflight the daemon already
refuses, and it leans on no header a proxy can strip — which is why the rule was tightened rather
than `hono/csrf` added.

Two callers were sending nothing where the daemon now wants a media type: `openapi-fetch` sets the
header only where there is a body to serialise, so `createApi` sets it on writes that carry none
(`packages/client/src/api/http.ts:11-30`), and Swagger UI does the same, so the playground gained a
`requestInterceptor`. A full-stack test retires a destination over the real transport, and fails
without the client half.
