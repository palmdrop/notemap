# Review: The run story — notemap as a published container

**Date**: 2026-08-27
**Status**: Resolved
**Scope**: PR #32, `agent/run-story` vs `main` — `Dockerfile`, `.dockerignore`, `docker/compose/`, `.github/workflows/release.yml`, `scripts/release.ts`, `apps/daemon/src/version.ts`, `README.md`, `docs/running.md`, `docs/specs/security.md`, `docs/specs/http-v1.md`
**Plan**: `docs/plans/run-story.md`
**Spec**: `docs/specs/security.md`, `docs/specs/http-v1.md`

---

## Overall

The shape is right and the reasoning in the amendment is better than what it replaced: a published
image, two whole compose files rather than a file that cannot run on its own, `pnpm fetch` off the
lockfile, and a version the daemon will tell you. Typecheck, lint, format and `pnpm -r test` are all
green, and running the suite leaves the tree clean, so the release script's clean-tree guard holds.

The important finding is that **the image tags the docs tell you to run are not the tags CI
publishes**. `type=semver,pattern={{version}}` strips the `v`, so a release is `0.2.0`, while
`docs/running.md` and `scripts/release.ts` both say `v0.2.0`. Anyone following the upgrade section
gets `manifest unknown`. Behind that sits a structural gap: nothing builds the image before a tag
names it — `release.yml` never runs on a pull request and `verify.yml` never runs `docker build` —
so a broken Dockerfile is discovered by the release that was supposed to ship it.

## Bugs

### 1. The published tag has no `v`; the docs and the release script say it does

`.github/workflows/release.yml:56` — `type=semver,pattern={{version}}` parses `refs/tags/v0.2.0` as
semver and emits `0.2.0`. `{{major}}.{{minor}}` emits `0.2`. So GHCR holds `0.2.0`, `0.2`, `latest`
and `sha-<short>`, and holds nothing called `v0.2.0`.

Three places claim otherwise:

- `docs/running.md:109` — `$EDITOR .env  # NOTEMAP_VERSION=v0.2.0`
- `docs/running.md:121` — the tag table's `` `v0.2.0`, `0.2` `` row, and `:232`, which says CI
  pushes `v0.2.0`
- `scripts/release.ts:140` — `release: CI is building ghcr.io/palmdrop/notemap:v0.2.0`

```
release prints v0.2.0 → operator writes NOTEMAP_VERSION=v0.2.0 → docker compose pull
  → ghcr.io/palmdrop/notemap:v0.2.0: manifest unknown
```

Fix: pick one form. Either add `type=raw,value=${{ github.ref_name }}` to the metadata tags so
`v0.2.0` exists too, or drop the `v` from the doc, the table and the script's closing line. The
second is less to carry — the tag in git keeps its `v`, the image does not.

### 2. `docs/running.md`'s first step cannot work: the repo is private

`docs/running.md:16-20` — the fetch is an unauthenticated `curl -L` at
`https://github.com/palmdrop/notemap/archive/refs/heads/main.tar.gz`. `gh repo view` reports the
repo `PRIVATE`, so that URL answers 404 and `tar xz` fails on an HTML body. The paragraph twelve
lines down already knows the *package* needs a login; the tarball needs one too.

Fix: authenticate the fetch (`gh repo clone`, or `curl -H "Authorization: Bearer $PAT"` against the
API tarball endpoint), or say plainly that the four files come out of a clone — which is the other
half of the sentence at `:22` and is the only path that works today.

### 3. A failed `git` call between the bump and the commit leaves the bump behind

`scripts/release.ts:85`, `:119-120` — `abandon()` exists because "by the time anyone can ask, the
bump is already written and has to be put back first", but only the tag-conflict *answer* routes
through it. Every other git call in that window is `run()`, which calls `fail()` and
`process.exit(1)` with the manifest still modified:

```
pnpm version writes 0.2.0 → git ls-remote fails (no network, expired credential)
  → run() → fail() → exit 1, package.json still says 0.2.0
  → next `pnpm release` refuses: "the working tree has changes; commit or stash them first"
```

`git add` and `git commit` at `:118-119` have the same hole. The recovery is a `git checkout --
package.json` the operator has to work out for themselves, from an error that does not mention it.

Fix: route the git calls made after the bump through `abandon()` rather than `run()` — either a
second helper, or a `try`/`catch` around everything from `tagConflict` to `git tag` that reverts the
manifest before reporting.

## Design

### 4. Nothing builds the image before a tag names it

`.github/workflows/release.yml:3-6` runs on `push` to `main` and on `v*` tags, never on
`pull_request`; `verify.yml` runs typecheck, lint, format, tests and the stack suite, and no
`docker build`. So this PR — which adds the Dockerfile — has never had its Dockerfile built by CI,
and `pnpm release` runs five checks that all pass without the image being one of them.

The failure mode is the expensive one: `pnpm release minor` passes, commits, tags and pushes, and
the image build fails afterwards. What is left is a `chore(release)` commit and a tag on `origin`
naming a version that exists nowhere, and `--atomic` cannot help because the thing that failed is
downstream of the push. Fixing it means either force-moving a pushed tag or burning a version.

Fix: build the image (`push: false`, `load: false`) as a job in `verify.yml`, so a PR proves the
Dockerfile before it can be released from.

### 5. The shipped `.env` defaults to a tag that does not exist

`docker/compose/.env:3` ships `NOTEMAP_VERSION=latest`, and `latest` is only pushed on a `v*` tag
(`release.yml:59`). `git tag` is empty — no release has been cut — so the first `docker compose up
-d` off the files as shipped fails to pull.

It is also the one value both the file's own comment and `docs/running.md:114-116` argue against.
Shipping the default the docs tell you not to use puts the loud warning in the one place a reader
has already skipped.

Fix: leave `NOTEMAP_VERSION=` unset with the comment naming what to put there, so a missing pin
fails at `up` with a readable message instead of pulling whatever `latest` becomes; or ship the
current release once one exists.

### 6. "Running both at once is the union" is not what happens

`docs/specs/security.md:124` — both compose files declare `name: notemap` and one service,
`notemap`. Running `docker compose up -d` and then `docker compose -f compose.proxy.yaml up -d` is
one project reconciled twice: the second recreates the container to match the second file, so what
you are left with is the proxy arrangement alone — no published port. The union only happens under
`docker compose -f compose.yaml -f compose.proxy.yaml up`, which merges rather than replaces.

As written, the sentence warns about a state the shared project name makes unreachable by the
reading most people will take, and stays silent about the invocation that does produce it.

Fix: name the invocation — merging the two files with `-f … -f …` gives the union; running one
after the other replaces rather than adds.

### 7. `scripts/release.ts` is typechecked by nothing

Root `scripts/` appears in no `tsconfig.json` — `apps/daemon` includes its own `src` and `scripts`,
every other package includes `src`, and there is no root project. `pnpm -r typecheck` therefore
never sees `scripts/release.ts`, and `node scripts/release.ts` strips the types rather than checking
them. `eslint .` covers the file, which catches shape but not types.

This is pre-existing for `dev.ts` and `seed.ts`, so it is not a regression — but `release.ts` is the
script that pushes tags to `origin`, and it is the one worth having checked.

Fix: a root `tsconfig.json` including `scripts`, wired into a root `typecheck` script.

## Minor

### 8. The plan describes two networks; the compose file joins one

`docs/plans/run-story.md:143-144` still reads "the service joins the proxy's network **and its
own**, and not the default one". `compose.proxy.yaml` declares `networks: [proxy]` — one network,
the external one. `security.md` as landed says one network, correctly; the plan line was not carried
across in the amendment's rewrite.

### 9. The health check in "Checking on it" only answers under one of the two files

`docs/running.md:100` — `curl -s http://127.0.0.1:4747/v1/health` in a section that follows both
arrangements. Under `compose.proxy.yaml` nothing is published on the host and that curl gets
connection refused. `docker compose exec` or the proxy's hostname is the equivalent there.

### 10. `.dockerignore` excludes build output except the daemon's `public/`

`.dockerignore:3-7` excludes `dist` and `build` at any depth, on the stated principle that "anything
already built on the host is a different machine's answer to the same question".
`apps/daemon/public/ui` and `apps/daemon/public/vendor` are that same host build output, are
gitignored, and are not excluded — so they ride into the context. `bundleUi()` `rmSync`s
`public/ui`, so that one cannot go stale, but `vendorSwaggerUi()` only overwrites its two named
files: an extra file left under `public/vendor/swagger` on the host ships in the image.

### 11. The pnpm version is pinned in three places

`Dockerfile:6` `corepack prepare pnpm@11.20.0`, `package.json:25-29`
`devEngines.packageManager.version: 11.20.0`, and `verify.yml` / `release.yml`'s
`pnpm/action-setup` at `version: 11`. Nothing holds them together, and the Dockerfile's is the one
that will be forgotten.

### 12. The fine-grained-PAT claim is stated absolutely

`docs/running.md:31-32` — "GHCR does not accept fine-grained tokens." GitHub has been extending
fine-grained PAT support to Packages, so this is worth re-verifying before it sends someone to
create a classic token they do not need. A dated qualifier would age better than a flat statement.

### 13. The 200's description does not mention what was added to the 200

`apps/daemon/src/routes/definitions.ts:130` — the response description is still "The daemon is up,
and this is the pool it holds." The summary and the route description both gained the version; this
line, which is the one rendered next to the body in the playground, did not.

### 14. `linux/amd64` only

`release.yml` builds one platform. Fine for the machine this plan was written for; worth knowing
before the image is pointed at anything ARM, which a homelab often is.

## Non-issues

- **`node -p "require('./package.json').version")` under `"type": "module"`** — `--eval` input is
  CommonJS regardless of the nearest manifest's type. Verified: prints `0.0.0`.
- **`tar xz --strip-components=3 '*/docker/compose'` without `--wildcards`** — both GNU and BSD tar
  glob member names on extraction by default, and 3 is the right depth for
  `notemap-main/docker/compose/…`. It is finding 2 that breaks this line, not the flags.
- **`expect(warnings).toEqual([])` in the container-config test** — not vacuous. `parseConfig`
  builds warnings from `droppedKeys`, so an unknown table in `docker/compose/config.toml` fails it.
- **`VOLUME /var/lib/notemap` in the Dockerfile** — compose names the volume anyway; the declaration
  only costs an anonymous volume to a bare `docker run`.
- **`VERSION` sentinel `0.0.0-dev` beside a root version of `0.0.0`** — deliberate, and the regex in
  `version.test.ts` accepts both. A test run and an unbuilt run are honestly distinguished.
- **`stop_grace_period: 30s` against `SHUTDOWN_GRACE_MS = 2_000`** — generous on purpose, for a
  delivery still in flight.
- **Plan **Status** is `In progress` with phase 5's verify unchecked** — honest: the machine has
  neither the phone nor the proxy. Both listed specs already carry dated `Shipped:` entries, so the
  trail is complete regardless of the status.
- **Only the root `package.json` version moves in a release** — one number for the daemon, the app
  and the image, which is what the build's `define` bakes in.

## The other review

This one was written blind, and reconciled afterwards against four comments on PR #32. Nothing
overlapped — no finding was reached by both — so the four are listed here as findings 15 to 18 and
were settled the same way.

15. Remove the doc comment on `VERSION` (`version.ts`).
16. Comments in shipped files must not be written from the development machine's point of view;
    treat everything in the repo as public.
17. `compose.proxy.yaml` presumes the reader's setup; it should read as an example for a
    hypothetical deployment behind a proxy.
18. Does notemap expect `/etc/notemap/config.toml`, when the default was `~/.config/notemap`?

## Resolution

1. **Fixed.** `release.yml` now uses `pattern=v{{version}}` and `pattern=v{{major}}.{{minor}}`, so
   the image tags carry the `v` the git tag does. `running.md`'s table and its release section say
   `v0.2.0`, `v0.2`; `release.ts` was already right.
2. **Fixed.** The tarball is gone. `running.md` clones with `gh repo clone --depth 1` and copies
   `docker/compose/` out of it, and says the repository is private up front.
3. **Fixed.** `release.ts` carries an `unwind` action that `fail()` runs before reporting: the
   manifest is discarded up to the commit, and the commit is reset up to the tag. Past the tag it is
   cleared, because the push failure is the one worth keeping — its message says how to retry.
4. **Fixed.** `verify.yml` gained an `image` job that builds the Dockerfile with `push: false`, so a
   PR proves it before a release can name it. Verified locally: `docker build` succeeds, and both
   compose files pass `docker compose config -q`.
5. **Won't fix.** Deliberate: `latest` stays the shipped default, and the comment beside it and
   `running.md` both argue for pinning.
6. **Fixed.** `security.md` names the invocation. Merging with `-f … -f …` is the union; running one
   file after the other replaces the container, and what is exposed is whichever was named last.
7. **Fixed.** A root `tsconfig.json` includes `scripts`, `@types/node` is a root devDependency, and
   `typecheck` runs `tsc -p tsconfig.json` before `pnpm -r typecheck`. `release.ts`, `dev.ts` and
   `seed.ts` are checked, under `erasableSyntaxOnly` since node strips their types rather than
   compiling them.
8. **Fixed.** The plan's phase 4 says one named network, which is what `compose.proxy.yaml` joins.
9. **Fixed.** `running.md` says that address is `compose.yaml`'s, and gives the `exec` form for the
   proxy arrangement.
10. **Fixed.** `.dockerignore` excludes `apps/daemon/public/ui` and `apps/daemon/public/vendor`.
11. **Fixed.** `11.20.0` is written once, as `packageManager` in the root manifest. The Dockerfile
    copies that manifest in beside the lockfile and runs `corepack enable`, which reads the version
    from it; both CI jobs dropped their `version:` input, which `pnpm/action-setup` then takes from
    the same field. `devEngines.packageManager` became the range `11.x`, so it states the
    requirement rather than repeating the pin. Verified: a build downloads exactly
    `pnpm-11.20.0.tgz` and installs with `pnpm v11.20.0`.
12. **Fixed.** The claim is no longer absolute — the classic token is named as the form that has
    always worked, with a note to check the current state of fine-grained support.
13. **Fixed.** The 200's description mentions the version; `openapi.json` and the client's generated
    types regenerated.
14. **Won't fix.** `linux/amd64` only, deliberately, until something ARM needs to run it.
15. **Fixed.** The comment is gone; the `-dev` suffix says what it said.
16. **Fixed.** `config.example.toml` opens on "a daemon run directly on a host" rather than "this
    machine", and the container pointer is stated rather than asked.
17. **Fixed.** Both compose files and `.env` are rewritten for a reader who is not the author: no
    "your other apps", no proxy presumed to exist already, and the network comment describes what
    the network has to be rather than what one particular host's is.
18. **Answered, and written down.** notemap does not expect it: `defaultConfigPath()` is still XDG,
    and `/etc/notemap/config.toml` exists only because the image's `CMD` passes `--config`. Kept —
    in the container the daemon runs as `node`, and mounting an operator's read-only file into a
    service account's home is worse than `/etc`. Both compose files and `running.md` now say that
    the path is the image's choice and name the XDG default beside it.
