# Review: Asset upload and images

**Date**: 2026-08-12
**Status**: Partially addressed
**Scope**: `agent/asset-upload-and-images` — `main..HEAD`, 9 commits
**Plan**: `docs/plans/asset-upload-and-images.md`
**Spec**: `docs/specs/core.md`, `docs/specs/http-v1.md`, `docs/specs/mirror.md`, `docs/specs/security.md`

## Overall

The slice does what it set out to do, and the doc-first ordering paid off: ADR 16, the four
specs and the code agree with each other everywhere I checked, the `Shipped:` trail is complete
on all four specs, and the test suite covers every property the plan called dangerous — two
names over one blob, the refcount under sweep, the grace window, a non-UTF-8 round trip,
attachment for anything not inert. `pnpm typecheck && pnpm test && pnpm lint` all pass in the
working tree.

**They do not pass from a clean checkout.** `.gitignore`'s `assets/` entry silently swallowed
`apps/daemon/src/assets/`, so three source files the daemon cannot start without were never
committed. That is finding 1 and it invalidates phase 8's "from a clean checkout" claim.

Everything else is small. Finding 2 is the only other one that defeats a stated property.

## Bugs

### 1. Three daemon source files are untracked; `HEAD` does not build

`.gitignore:14` — the entry `assets/` is meant for a pool's blob directory. It is a bare
directory name with no leading slash, so git applies it at **every** depth, and
`apps/daemon/src/assets/` matches:

```
$ git check-ignore -v apps/daemon/src/assets/content-disposition.ts
.gitignore:14:assets/	apps/daemon/src/assets/content-disposition.ts
```

`git status` is clean, `git add` is a no-op without `-f`, and nothing in the working tree ever
complains — the files are right there. But a `git worktree add --detach HEAD` has no
`apps/daemon/src/assets/` at all, and three modules import from it:

```
apps/daemon/src/main.ts:8            import { startSweeper } from "./assets/sweeper";
apps/daemon/src/routes/assets.ts:10  import { … } from "../assets/content-disposition";
apps/daemon/src/routes/assets.ts:11  import { dispositionFor } from "../assets/disposition";
apps/daemon/src/testing/fixture.ts:17 import { startSweeper } from "../assets/sweeper";
```

```
gitignore matches at any depth → src/assets/ never staged → clean checkout has no
disposition.ts / content-disposition.ts / sweeper.ts → daemon typecheck, tests and start all fail
```

So the upload route, the inline/attachment allowlist — the one property the plan calls a
security bug when it regresses — and the sweep loop are all absent from the branch as committed,
and the tests that cover them cannot run.

Fix: anchor the pattern to the pool directories it was written for (`/assets/` at the root, or
the `data/`-relative paths), then `git add -f apps/daemon/src/assets/` and amend. `state/`,
`data/` and `pool-mirror/` on lines 11–13 have the same shape and the same latent problem —
worth anchoring in the same change. A cheap guard against the recurrence is running the phase
verification in a throwaway `git worktree` rather than in place.

### 2. A malformed `Repr-Digest` is silently ignored, not refused

`apps/daemon/src/routes/assets.ts:155` — `sha256From` returns `undefined` for anything it cannot
parse, and `guarded` treats `undefined` as "the client offered no digest". RFC 9530 lets a
recipient ignore an algorithm it does not support; it does not license ignoring a **supported**
algorithm whose value is malformed. Measured:

```
"sha-256=:!!!!:"                → 0 bytes  → ignored, 201
"sha-256=:abc:"                 → 2 bytes  → ignored, 201
"sha-256=47DEQ…FU="  (no colons)→ no match → ignored, 201
```

The last is the interesting one: omitting RFC 9530's byte-sequence colons is the obvious client
mistake, and it produces a `201` from a client that believes its bytes were verified.
`http-v1.md:232` promises the header is "checked against the bytes received", and D2 calls this
check the load-bearing half of integrity now that `AssetRef` carries no hash.

Fix: distinguish "no `sha-256` entry" from "a `sha-256` entry that is not 32 base64-encoded
bytes". The first stays ignored; the second is `422 digest-mismatch` (or a new code) before any
bytes are read. `assets.test.ts` covers the mismatch case but not the malformed one.

## Design

### 3. `Pool.assets.store` declares a refusal it can never return

`packages/core/src/pool/assets.ts:13` returns `Result<Asset, AssetRefusal>`, but `AssetRefusal`
is `no-such-asset | blob-missing` — neither is reachable from a store path, and the function has
no `refused` return. The consequence is dead error handling at every call site:
`routes/assets.ts:54` has an `if (result.kind === "refused")` branch that cannot be taken, and
both fixtures (`tests/integration/src/fixture.ts:265`, and the daemon's) throw on a branch that
never runs.

Every refusal an upload can actually raise — `asset-too-large`, `digest-mismatch`,
`missing-filename` — lives in the daemon, which is right: a cap is interface policy and core is
a primitive API. So the honest signature is `Promise<Asset>`, and the `Result` should come back
only if core gains a refusal of its own.

### 4. Nothing ever reclaims a blob that no asset row ever named

`packages/core/src/pool/assets.ts:18` writes the blob, then inserts the row in a separate
transaction. The comment names the crash window and calls the cost space — fair. But the sweep's
only entry point is `unreferencedAssets`, which selects from the `assets` table
(`pool-store.ts:232`), so a blob with no row is invisible to it *forever*, not just until the
next run. The mitigation the comment offers — "the next identical upload reuses it" — only holds
for a repeat of those exact bytes.

The same applies to `.notemap-*` temporaries after a hard kill: `blob-fs/src/paths.ts:5` calls
the prefix "what a sweep of the directory may remove", and no sweep of the directory exists.
`store.ts:70` covers the graceful failure, and the test proves it, so this is only the SIGKILL
case.

Not worth building now — it is what deep verify or rebuild is for — but it is a second kind of
leak that the sweep's name currently implies it handles, and `CONTEXT.md`'s new **Sweep** entry
reads as if the loop is closed. Worth one sentence there, or an entry under `http-v1.md`'s open
questions, so the next person does not assume it.

## Minor

### 5. `Content-Length` is served from the row, not the file

`apps/daemon/src/routes/assets.ts:92` sets `content-length: String(asset.bytes)`. Downloads
deliberately do not rehash (D4), which is right — but a drifted blob that also changed *size*
turns a silent inconsistency into a protocol error: the response advertises N bytes and delivers
something else, and the client sees a truncated or hanging transfer rather than a bad file.
Omitting the header lets the transfer chunk and fail honestly, at the cost of no progress bar.

### 6. `sweeper.run()` still works after `stop()`

`apps/daemon/src/assets/sweeper.ts:29` — `stopped` is checked in the interval callback but not
in `run()`, so a direct call after `stop()` starts a fresh sweep against what may be a closed
pool. Only tests call `run()` directly today (`testing/fixture.ts`), and they call it before
`cleanup()`, so nothing fires. One line in `run()` closes it.

### 7. Two ICO/WAV spellings fall through to `attachment`

`apps/daemon/src/assets/disposition.ts:16` lists `image/x-icon` and `audio/wav`. The IANA
registration for ICO is `image/vnd.microsoft.icon`, and `audio/x-wav` / `audio/vnd.wave` are
both common in the wild. They download instead of rendering — fail-closed, which is the right
direction, so this is a completeness note rather than a defect.

### 8. The sweep drains at 12k orphans/day

`packages/core/src/pool/maintenance.ts:15` caps a run at 500, and `constants.ts:32` runs one
hourly. The reasoning for both is sound in isolation, but together a pool that accumulated a
large orphan pile clears it slowly. Nothing to change now — worth knowing before the numbers are
tuned for a real workload.

### 9. The capture page renders `<img>` for every asset of every payload type

`apps/daemon/public/index.html:233` loops over `item.payload?.assets` regardless of
`payload.type`. The moment a payload type with an audio slot is configured, the feed shows
broken images. It is the throwaway page, so this is only worth doing when a second slot-carrying
type lands.

## Non-issues

- **Phase 7's unchecked box** — `plans/asset-upload-and-images.md:277`. The `Content-Disposition`
  subresource assumption is unverified because nothing here drives a browser, and the plan argues
  it is not load-bearing (every raster type is on the inline allowlist). Deliberate, stated, with
  a fallback. The plan is still correctly `Done`.
- **`recordFor` silently drops an unresolved asset** — `core/src/pool/mirror.ts:36`. A foreign key
  stands under every reference after migration 8, so the filter is unreachable, and failing there
  would break that item's mirror write forever. Correct call.
- **Two migrations touching `item_assets` back to back** — the first drops `hash`, the second
  recreates the table for the foreign key. Redundant in a fresh database, but migrations are
  append-only and phase 2 shipped before the `assets` table existed.
- **`PRAGMA foreign_keys = ON` before `migrate()`** — `pool-store.ts:135`. SQLite's table-rebuild
  recipe wants foreign keys off, but `item_assets` is a child in both migrations and no other
  table references it, so no rewrite or cascade can fire.
- **The blob store's `pathFor` handed to the mirror renderer** — the layout belongs to the blob
  driver and the mirror asks rather than composing a second copy. Right seam.
- **`requireJsonBody` carved out by exact path** — `middleware/content-type.ts:18`. By equality
  rather than prefix, so a future `/v1/assets/*` route cannot quietly lose the guard.
